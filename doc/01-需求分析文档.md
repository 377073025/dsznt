## 1. 背景与参考视频拆解

### 1.1 视频核心观点

博主展示的是他自建的 **AI Native 公司系统** 中的「电商模块」。一句话概括：

> **接数据 → 看数 → 给建议 → CEO 汇总 → 店主拍板 → 派活 → 验收 → 回流**，7 步转一圈，形成闭环。
> 原则：**建议先交 CEO，再到店主**；店主只跟 CEO 一个说话，不用盯每一个 AI。

视频结尾总结的「三句话，记住这个圈」：

1. **先接数据，再谈 AI** —— AI 看不到的东西，它判断不了。
2. **建议先过 CEO，店主只管拍板** —— AI 看数、给建议，CEO 汇总、派活、验收。
3. （画面未完整截到，按上下文推断）**做完要验收，结果回流成新数据** —— 每转一圈，店就多一分有数。

### 1.2 全局架构（视频 4:20 起「公司运转图」）

```
              Simon（创始人：拍板、定方向）
                  ↑ 汇报·每天按点      ↓ 拍板·定方向
              CEO Agent（收汇报、派活、验收；盯着每一块转没转）
     ┌──────────┬──────────┬──────────┬──────────┬──────────┐
  电商 Agent   内容 Agent   仓库 Agent   投资 Agent  运营·知识库   巡检 Agent
   「看店」      「看号」      「看仓库」     「研究」      「整理」       「巡检」
     │
  店铺 A / B / C / D（各自流量、订单）
```

本期只做 **电商 Agent** 这一块，但架构上要给其他模块留位置。

### 1.3 7 个环节（视频原图内容）

| # | 环节 | 执行者 | 做什么 | 原则 |
|---|------|--------|--------|------|
| 01 | 接数据 | 程序自动收 | 店铺后台、订单通知，每天按点收进来 | AI 看不到的，它判断不了；拿不到就直说，不估 |
| 02 | 看数 | AI · 只读 | 来了多少人、多少加购、多少下单，哪一步掉了 | 只看不碰店铺：看错了，最多写错一句话 |
| 03 | 给建议 | AI · 只读 | 只说一句：「建议……，因为……」 | 带着理由，店主才判断得了对错 |
| 04 | 店主拍板 | 人 | CEO 报上来的：同意、不同意，或者改一改 | 上新、下架、对外回复，只有人能点头 |
| 05 | 动手 | AI 干活 | 出图、写标题和描述、建商品、上架 | 只接批过的活；真动店铺前，再问店主一次 |
| 06 | 验收 | CEO 来查 | 做完了没有？做对了没有？ | 说做完不算，查过才算；不过就返工 |
| 07 | 回流 | 回到起点 | 卖得怎么样，第二天又是新数据 | 每转一次，店就多一分有数 |

中枢 **CEO Agent（管流程）**：
- **汇总**：几条建议合成一份，每天按点报店主
- **派活**：店主点了头，再交给干活的 AI
- **验收**：干完对着要求查，就是 06 这一站

### 1.4 视频中的两个示例（店和数字均为示例）

**示例 A：AI 每天看流量，报店铺情况（店铺早报）**

- 整店漏斗（昨天）：访客 1,240（比上周同一天 +20%）→ 加购 74（6.0%）→ 下单 31（41.9%）
- 分款看（昨天）：

| 款 | 访客 | 加购 | 加购率 | 下单 |
|----|------|------|--------|------|
| 柑橘 | 380 | 34 | 8.9% | 16 |
| 海盐 | 420 | 13 | **3.1%（上周 8.2%）** | 4 |
| 薰衣草 | 260 | 18 | 6.9% | 8 |
| 其他 | 180 | 9 | 5.0% | 3 |

- 早报结论：
  - **最好卖**：柑橘，下单 16，加购率 8.9%，全店最高
  - **正常**：薰衣草和其他款，跟上周差不多，一句带过
  - **掉在哪**：海盐看的人最多（420），加购率却从 8.2% 掉到 3.1%。人来了，是商品页没留住
  - **建议**：把海盐的第一张图换回点燃的那张，**因为**加购率是从换成白底图那天开始掉的
- 底部操作：「先交 CEO，汇总后报店主拍板」 → **同意 / 不同意 / 改一改**

**示例 B：上新品，完整走一圈**

1. 看数：柑橘连着两周卖得最好，三成是回头客
2. 给建议：建议加两款同系列新香型——葡萄柚、青柠
3. CEO 汇总 → 店主拍板：「同意，做葡萄柚和青柠」
4. CEO 派活：出图、写标题和描述，先放草稿；**上架前再问一次**
5. 动手：两款上架了
6. CEO 验收：两款都上齐了吗？图、标题、香型对得上吗？
7. 回流：一周后看新款多少人看、多少人下单（葡萄柚 310 人看 12 单；青柠 260 人看 9 单），一周后的数据回到起点

### 1.5 评论区有价值的信息

| 观点 | 对本项目的启示 |
|------|----------------|
| 「能拿到所有数据才是大问题」——作者：「对，这个要认真解决，根基。能搞定的，看平台」 | **数据接入是第一风险**，必须按平台逐个解决，MVP 允许手动导入 |
| 「适合一件代发的小店铺吗？」——作者：「特别适合」 | 目标用户：中小店铺 / 一人电商 |
| 「这只是把数据流渲染成图表，真正有作用的是每个板块的分析诊断处理的逻辑」（6 赞） | 价值在**诊断逻辑**，不在可视化，要重点设计归因规则 |
| 「老电商的话实在是用不到」「ERP 都有」 | 差异化在「建议+拍板+执行+验收」闭环，而不是报表 |
| 作者不开源，「给你们讲思路，自己开发」 | 需要自研 |

## 2. 产品定位

### 2.1 一句话定位

**一个替店主「看店、出主意、干活、查活」的 AI 团队，店主每天只需要看一份报告、点几次「同意」。**

### 2.2 目标用户

| 用户 | 特征 | 核心诉求 |
|------|------|----------|
| 一人店主 / 夫妻店（主要） | 1–3 人，1–4 家店，一件代发或小批量自营 | 没时间盯数据；不懂分析；想把重复的出图、写标题交出去 |
| 小团队运营负责人（次要） | 3–10 人，多店铺 | 把日常诊断标准化，自己只做决策 |

### 2.3 要解决的问题

1. **看不过来**：多个店、多个后台，每天数据散落各处
2. **看不出原因**：知道销量掉了，不知道掉在漏斗哪一步、和什么改动有关
3. **想到做不到**：知道要换图、上新，但出图、写文案、建商品很耗时
4. **做了没跟踪**：改了之后效果如何，没人回头看

### 2.4 设计原则（必须遵守）

| 编号 | 原则 | 说明 |
|------|------|------|
| P1 | 数据优先 | 没有数据不分析；数据缺失时明确说「拿不到」，**禁止估算** |
| P2 | 分析只读 | 看数、给建议的 AI 没有任何写店铺的权限 |
| P3 | 建议带理由 | 每条建议必须是「建议……，因为……」，理由要能对应到具体数据 |
| P4 | 单一入口 | 店主只和 CEO Agent 交互，不直接面对多个 AI |
| P5 | 人来拍板 | 上新、下架、改价、对外回复等对店铺有影响的动作，必须店主批准 |
| P6 | 二次确认 | 即使已批准，真正写入店铺（上架/发布）前再确认一次 |
| P7 | 验收才算完 | 执行结果必须经 CEO 对照要求检查，不通过则返工 |
| P8 | 结果回流 | 每个执行动作都要在之后的数据里被追踪效果 |
| **P0** | **人工尽量少（项目基准）** | 能自动的全部自动；人工只保留在决策闸门、平台限制、自动失败兜底三种情况；每个环节按「自动 → 半自动 → 人工兜底」设计（详见 [04 号文档](04-选品智能体与可行性复评.md) 第 1 节） |

## 3. 功能需求

优先级：P0 = MVP 必须；P1 = 第二阶段；P2 = 后续规划。

### 3.1 F1 数据接入（环节 01）

| ID | 需求 | 优先级 |
|----|------|--------|
| F1.1 | 支持手动上传店铺后台导出的报表（CSV/Excel）：流量、商品、订单 | P0 |
| F1.2 | 定时任务每天固定时间（可配，默认 07:00）拉取/读取前一天数据 | P0 |
| F1.3 | 支持多店铺，每个店铺独立配置数据源 | P0 |
| F1.4 | 对接平台开放 API（优先抖店，其次淘宝/天猫、拼多多、小红书） | P1 |
| F1.5 | 记录店铺「改动事件」（换主图、改价、改标题、上新），用于归因 | P0（手动录入）/ P1（自动识别） |
| F1.6 | 数据完整性检查：缺字段、缺日期时标记「数据缺失」，下游不得估算 | P0 |
| F1.7 | 订单/售后等实时通知接入（Webhook 或消息推送） | P2 |

**最少需要的数据字段**：日期、店铺、商品（款）、访客数、加购数、下单数、支付金额、退款数；商品维度的主图、标题、价格变更记录。

### 3.2 F2 看数 / 诊断（环节 02，AI 只读）

| ID | 需求 | 优先级 |
|----|------|--------|
| F2.1 | 整店漏斗：访客 → 加购 → 下单，计算各层转化率 | P0 |
| F2.2 | 同比对比：默认对比「上周同一天」，可选环比前一天、近 7 日均值 | P0 |
| F2.3 | 分款明细：每个商品的访客、加购、加购率、下单 | P0 |
| F2.4 | 异常检测：识别「掉在哪一步」（流量掉 / 加购率掉 / 下单率掉），阈值可配 | P0 |
| F2.5 | 归因：把异常与同期改动事件关联（如「加购率从换白底图那天开始掉」） | P0 |
| F2.6 | 亮点识别：最好卖款、连续增长款、回头客占比高的款 | P1 |
| F2.7 | 分级输出：最好卖 / 正常（一句带过）/ 掉在哪 | P0 |

### 3.3 F3 给建议（环节 03，AI 只读）

| ID | 需求 | 优先级 |
|----|------|--------|
| F3.1 | 每条建议固定格式：「建议……，因为……」，并附引用的数据依据 | P0 |
| F3.2 | 建议类型：优化类（换图、改标题、改价）、上新类、下架类、库存类 | P0（优化/上新）/ P1（其他） |
| F3.3 | 每条建议标注：涉及店铺、商品、预期影响指标、风险等级 | P0 |
| F3.4 | 建议去重：同一问题未处理时不重复生成新建议，改为「仍未处理」提醒 | P1 |

### 3.4 F4 CEO Agent（汇总 / 派活 / 验收）

| ID | 需求 | 优先级 |
|----|------|--------|
| F4.1 | 汇总：将各店铺、各模块的建议合并为一份「店铺早报」，每天定时推送 | P0 |
| F4.2 | 早报结构：漏斗概览 → 分款亮点/异常 → 建议列表（每条可操作） | P0 |
| F4.3 | 排序：按影响大小和紧急度排序，单份早报建议不超过 5 条（可配） | P1 |
| F4.4 | 派活：店主同意后，把建议拆成具体任务，分派给对应执行 Agent | P0 |
| F4.5 | 验收：任务完成后，按任务的验收标准逐项检查，不通过则退回返工（最多 N 次后升级给店主） | P0 |
| F4.6 | 店主可直接对 CEO 下达指令（如「把青柠价格改成 39」），由 CEO 走同样的派活流程 | P1 |
| F4.7 | 流程看板：每条建议/任务当前处于 7 步中的哪一步 | P0 |

### 3.5 F5 店主拍板（环节 04，人）

| ID | 需求 | 优先级 |
|----|------|--------|
| F5.1 | 每条建议三个操作：同意 / 不同意 / 改一改 | P0 |
| F5.2 | 「改一改」：店主用自然语言修改建议，CEO 重新整理后再确认 | P0 |
| F5.3 | 「不同意」可选填原因，用于后续优化建议质量 | P1 |
| F5.4 | 推送渠道：Web 页面（P0）、企业微信/飞书/钉钉机器人（P1）、手机 App（P2） | P0/P1/P2 |
| F5.5 | 二次确认：执行 Agent 在真正写入店铺前，再次请求店主确认 | P0 |

### 3.6 F6 动手（环节 05，AI 干活）

| ID | 需求 | 优先级 |
|----|------|--------|
| F6.1 | 只接受状态为「已批准」的任务，否则拒绝执行 | P0 |
| F6.2 | 出图：生成/替换商品主图、详情图（AI 生图或从素材库选图） | P0 |
| F6.3 | 写文案：商品标题、卖点、描述，符合平台规则（字数、违禁词） | P0 |
| F6.4 | 建商品：生成商品草稿（标题、图、规格、价格），**默认只存草稿** | P0 |
| F6.5 | 上架/修改：调用平台 API 写入店铺，二次确认后执行 | P1（MVP 由店主手动上架，系统给出完整物料包） |
| F6.6 | 每次执行留下操作记录（改了什么、改前/改后），支持一键回滚 | P1 |

### 3.7 F7 验收（环节 06）

| ID | 需求 | 优先级 |
|----|------|--------|
| F7.1 | 每个任务在派活时就生成验收清单（如：两款都上齐了吗？图、标题、香型对得上吗？） | P0 |
| F7.2 | CEO 逐项检查执行结果（读取店铺实际状态或执行产物），输出通过/不通过 + 原因 | P0 |
| F7.3 | 不通过自动返工；超过返工上限则报给店主 | P0 |

### 3.8 F8 回流（环节 07）

| ID | 需求 | 优先级 |
|----|------|--------|
| F8.1 | 每个已完成任务自动登记为「改动事件」，进入 F1.5 | P0 |
| F8.2 | 设定效果观察期（默认 7 天），到期后自动出效果复盘：改动前后关键指标对比 | P0 |
| F8.3 | 复盘结果进入下一轮看数，形成闭环；建议的历史采纳率与效果可查 | P1 |
| F8.4 | 知识沉淀：有效/无效的做法记入店铺知识库，供后续建议参考 | P2 |

### 3.8.1 F1 补充：数据双通道

| ID | 需求 | 优先级 |
|----|------|--------|
| F1.8 | API 通道与人工导入通道**都要做**，同一数据项可多通道获取，系统按优先级自动选择、失败自动降级 | P0 |
| F1.9 | 后台采集器：API 拿不到的数据（访客、加购、推广），用本地浏览器脚本在已登录后台定时导出，只读、低频、不用 LLM 驱动 | P0 |
| F1.10 | 采集失败时飞书通知人工导入，并在人工导入后自动补跑分析 | P0 |

### 3.8.2 F10 选品智能体（1688）—— 关键步骤，进入 MVP（可行性方案见 [05 号文档](05-选品智能体可行性方案.md)）

| F10.6 | 候选经 CEO 汇总后以飞书卡片推送，店主拍板后进入上新流程 | P0 |

| F10.9 | 以图搜货：为现有款寻找替代货源 | P1 |

## 4. 核心用例

### UC-1 每日店铺早报（对应示例 A）

1. 07:00 系统拉取昨天数据（F1）
2. 电商 Agent 计算漏斗和分款数据，识别「海盐加购率 8.2%→3.1%」（F2）
3. 关联改动事件「海盐主图换成白底图」，生成建议「把海盐的第一张图换回点燃的那张，因为加购率是从换成白底图那天开始掉的」（F3）
4. CEO Agent 汇总所有店铺的建议，08:00 推送早报（F4）
5. 店主点「同意」（F5）
6. CEO 派活：图片 Agent 恢复旧主图（F6），上线前二次确认
7. CEO 验收：主图已换回、与旧图一致（F7）
8. 登记改动事件，7 天后复盘海盐加购率（F8）

### UC-2 上新品（对应示例 B）

1. 看数：柑橘连续两周最好卖，三成回头客
2. 建议：加两款同系列新香型（葡萄柚、青柠），因为……
3. 店主「改一改」或「同意」
4. CEO 派活：出图、写标题和描述，先放草稿
5. 上架前二次确认 → 上架
6. 验收：两款是否都上齐、图/标题/香型是否对应
7. 一周后复盘新款访客与下单

### UC-3 数据缺失

1. 某店铺昨天数据未拉取到
2. 早报中该店显示「数据缺失：××字段未获取」，**不做任何推测性分析**
3. 提示店主手动上传或检查授权

## 5. 非功能需求

| 类别 | 要求 |
|------|------|
| 安全 | 平台 API 凭证加密存储；分析类 Agent 无写权限（权限隔离到工具层）；所有写操作留审计日志 |
| 可靠性 | 定时任务失败自动重试 3 次并告警；执行失败不影响其他任务 |
| 准确性 | 所有数字由程序计算，LLM 只负责解读和表述，不允许 LLM 自行计算或编造数字 |
| 可解释 | 每条建议可追溯到数据来源和计算过程 |
| 时效 | 早报在设定时间后 30 分钟内送达；单店分析 < 2 分钟 |
| 成本 | 单店每日 LLM 成本可控（目标 < ¥1/店/天，MVP 阶段统计实际值） |
| 合规 | 遵守各平台开放平台协议，不使用爬虫抓取后台；生成内容需过违禁词检查 |

## 6. 范围与分期

| 阶段 | 范围 | 目标 |
|------|------|------|
| **MVP（V0.1）** | 手动导入数据 + 漏斗/分款诊断 + 建议 + CEO 早报（Web）+ 同意/不同意/改一改 + 出图/写文案产出物料包 + 验收 + 7 天复盘 | 单店跑通 7 步闭环 |
| V0.2 | 抖店 API 自动接数；IM 机器人推送；商品草稿自动创建；操作回滚 | 每天无人值守跑早报 |
| V0.3 | 多平台、多店铺；自动上架（二次确认）；知识库 | 覆盖 1–4 家店 |
| V1.0 | 接入其他模块（内容、仓库等），完整「公司运转图」 | AI Native 一人公司 |

**MVP 明确不做**：自动改价、自动下架、自动回复买家、广告投放。

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 拿不到平台数据（评论区共识） | 闭环无法启动 | MVP 手动导入；V0.2 起逐平台申请开放平台权限；数据缺失时明确告知不估算 |
| 归因不准（把巧合当原因） | 建议错误，店主失去信任 | 归因只给「时间相关」证据并标置信度；建议必须人工拍板；复盘反馈修正 |
| LLM 编造数字 | 误导决策 | 数字只来自程序计算结果，LLM 输出做数字一致性校验 |
| AI 误操作店铺 | 实际损失 | 权限分离 + 店主批准 + 二次确认 + 草稿优先 + 回滚 |
| 建议太多变成噪音 | 店主不看 | 每日上限、按影响排序、同类合并、「正常」一句带过 |
| 平台规则限制（违禁词、图片规范） | 上架失败或违规 | 内置平台规则校验，验收环节检查 |

## 8. 成功指标
