## 1. 总结论

**项目可行，建议进入 POC。**

| 维度 | 结论 |
|------|------|
| AI 能力 | ✅ 不是瓶颈。看数、诊断、建议、汇总、选品判断、文案、看图验收都在现有模型能力范围内 |
| 数据获取 | ⚠️ **最大风险**。拼多多对小商家几乎不开放流量数据接口，1688/拼多多网页有风控；靠「API + 网页读取 + 人工导入」三通道兜住。每天只读 2–5 次，拼多多自家后台风险低；**风险集中在 1688 每周批量选品搜索** |
| 自动执行 | ⚠️ 上架、下单依赖第三方铺货代发工具或开放平台资质；可做到「半自动、人点一下」，所谓「闭环」实际是**半自动闭环** |
| 合规 | ⚠️ 履约风险（发货慢、断货、货不对板）靠 1688 供应商多维筛选拦截；商品本身的风险（类目资质、侵权、描述不符）靠类目黑名单、品牌词库和看图审查，两者互补 |
| 盈利 | ⚠️ 选品目标为「无货源、不亏」，判定口径是**扣除退货损失和推广费后的单款净利 > 0**，测款期每款设亏损上限 |
| 人工投入 | ✅ 日常可压到 **每天约 5 分钟**（飞书里点按钮），另每 1–4 周扫码登录一次 |
| Token 成本 | ✅ **不会花大量 token**：单店 LLM 费用约 **¥70–130/月**（含选品）；加生图后 AI 相关合计约 ¥100–280/月 |
| 总成本 | 主要成本是工具订阅（市场数据、铺货代发）和生图，不是 LLM |
| 未验证项 | 网页读取的风控稳定性、1688 详情字段可得率、AI 同款判断准确率、**选品命中率** |

## 2. 项目基准与已确认决定

**基准：人工尽量少。** 人工只保留在三种情况：决策闸门（拍板、确认上新、确认付款）、平台硬性要求（授权、扫码登录、验证码）、自动失败时的兜底。

| 决定 | 结论 |
|------|------|
| 平台 | 拼多多 |
| 模式 | 一件代发，货源 1688 |
| 交互渠道 | 飞书（主入口），Web 控制台为辅 |
| 出图 | AI 生成 + 素材库，两者都要（以修图、换背景、场景合成为主） |
| 部署 | 先本地部署 |
| 多用户 | 需要（店主 / 运营分权限） |
| 数据获取 | API 与人工导入两种都做；没有 API 的用网页读取 |
| 选品 | **关键步骤，由智能体完成，进入 MVP** |
| 选品目标（2026-10-26） | 做无货源，**只要不亏就行**：单款净利（扣除退货损失、推广费、扣点后）> 0；测款期每款设最大亏损额度 |
| 合规手段（2026-10-26） | 1688 卖家诚信度等多维度筛选（管履约风险）+ 类目黑名单、品牌词库、看图审查（管商品风险） |
| 网页读取（2026-10-26） | 每天 2–5 次；Playwright 操控真实浏览器、**读网页文本取数**；截图只用于 AI 认路、看图判断、字体混淆时识别数字，以及每次采集留存证据 |

## 5. 数据获取方案（最终）

### 5.1 三通道，自动降级

| 优先级 | 通道 | 用于 |
|--------|------|------|
| 1 | 开放平台 API | 有资质时：拼多多商品/订单、1688 搜索/拍立淘/详情 |
| 2 | 网页读取层 | API 拿不到的：拼多多后台访客/加购/关键词、1688 搜索与详情、市场数据工具页面 |
| 3 | 人工导入 | 前两者失败时；系统在飞书通知并给出操作指引 |

### 5.2 网页读取层的做法

在本地独立浏览器中使用已登录会话访问网页，**每天 2–5 次**：

| 层级 | 做法 | 场景 | 成本 |
|------|------|------|------|
| 固定脚本 | AI 首次摸清路线后录成脚本，每天按脚本跑，**直接读网页文本取数** | 日常 | ≈ ¥0 |
| AI 认路 | 页面改版、脚本失败时，AI 读页面结构重新找路，修好后更新脚本 | 偶发自愈 | 每次约 ¥0.5–2 |
| AI 看截图 | 只用于看图：同款判断、合规审查、上架后核对 | 少量 | 按张计 |

**不采用「全程截图让 AI 读数」**：数字可能读错、成本高几十倍（单店约 ¥250/月）、速度慢。而且**截图并不降低风控风险**：平台识别的是访问行为（频率、时间规律、浏览器指纹），读文本和截图打开页面的动作完全一样。

**截图的使用场景**（混合方案）：

| 场景 | 方式 |
|------|------|
| 日常取数 | 读网页文本 |
| 页面改版、脚本失效 | 截图 + 页面结构交给 AI 认路，修好后固化为新脚本 |
| 同款判断、合规看图、上架后核对 | 截图给模型看 |
| 页面用自定义字体打乱数字，或数据画在图表图片里 | 截图识别数字（是否存在由 POC 阶段 A 确认） |
| 每次采集 | 顺手存一张截图作为证据，便于事后核对，不调用模型 |

**风控影响因素与对策**：

| 因素 | 现状 | 风险 | 对策 |
|------|------|------|------|
| 每天次数 | 2–5 次 | 低，接近店主自己看后台 | — |
| 每次打开页数 | 后台概况几页；按单品拉数据，50 款 ≈ 50+ 页 | 单品数据量大时升高 | 优先用导出报表；设每日页数上限 |
| 1688 选品搜索 | 每周对几十到上百个候选以图搜货、看详情 | **主要风险点** | 独立采集账号；分几天分批跑；POC 实测验证码频率 |
| 自动化特征 | 无界面浏览器、自动化标记易被识别 | 取决于实现 | 用**有界面的真实 Chrome** + 长期固定的浏览器配置 |
| 登录环境 | 换电脑、换网络、频繁重新登录会触发异常检测 | 取决于部署 | 固定同一台电脑、同一网络，与人工登录环境一致 |
| 行为规律 | 整点准时、翻页无停顿 | 中 | 运行时间随机偏移；翻页间随机停顿几秒 |
| 验证码 / 访问受限 | — | — | **立即停止并通知人工**，不自动重试（熔断） |

结论：按以上做法，读拼多多自家后台基本可以放心。但严格说自动化访问仍不完全符合平台规则，常见后果是弹验证码或临时限制访问；拼多多后台用的是**店铺主账号**，仍应保守。

### 5.3 平台接口现状

| 平台 | 情况 |
|------|------|
| 拼多多开放平台 | 商家自研系统面向「有软件开发能力的大型商家」，小商家大概率申请不到；订单敏感数据需多多云；**单款访客/加购未找到公开接口** |
| 1688 开放平台 | 有搜索、详情、拍立淘图片搜索接口，需企业开发者资质和权限审核；分销铺货、自动下单多属于服务商合作范畴 |

## 6. 选品可行性（关键步骤）

**流程**：店内好卖款 / 拼多多热词 / 类目榜单 → 竞品主图 → 1688 以图搜货 + 关键词搜 → 硬性过滤 → AI 同款与合规审查 → 利润计算与 7 维度打分 → 推荐理由 → CEO 汇总 → 飞书拍板 → 铺货 → 14 天测款 → 留/改/汰 → 调权重。

| 判断点 | 结论 |
|--------|------|
| 技术上能否实现 | ✅ 每一步都有成熟手段 |
| 数据是否够用 | ⚠️ 需求端：拼多多后台关键词（官方、免费）+ 建议订阅一款市场数据工具（多多情报通 / 电霸）；供给端：1688 网页或接口 |
| 现成工具能否替代 | ❌ 市场数据工具只看需求端，铺货代发工具只看货源与履约，都不做综合打分，也没有公开 API；**作为数据源和执行工具使用** |
| 代发自动下单 | ✅ 由第三方代发工具完成；选品时识别「能否被代发工具自动下单」并计入评分 |
| 选得准不准 | ⚠️ 未知，只能通过离线回测和线上测款对照验证 |

选品规则（硬性过滤 10 条、打分 7 维度、利润公式、测款淘汰规则）见 [04 号文档 3.4–3.5 节](04-选品智能体与可行性复评.md)。

| 项目 | 估算 | 说明 |
|------|------|------|
| 运营闭环 AI 费用 | ¥30–60 | 看数、建议、汇总、派活、验收、复盘；已含缓存、Batch、模型分级优化 |
| 选品 AI 费用 | ¥40–50 | 每周一次完整选品约 ¥10 |
| 网页读取 | ¥0–20 | 固定脚本不耗 token；只有修路时花费 |
| 生图 | ¥30–150 | 按每天约 10 张、每张 ¥0.1–0.5 |
| **AI 相关合计** | **约 ¥100–280** | |

| 铺货代发工具 | 需询价 | 多有免费试用 |

模型分工：CEO 汇总与验收用 Claude Opus 5.5（$4 / $20 每百万 token），分析、选品审查、文案用 Sonnet 5.5（$2 / $10），同款初筛等简单活用 Haiku 5.5（$0.10 / $0.50）。

**会让 token 失控的做法（全部规避）**：把原始报表整张塞给 LLM；让 Agent 无上限循环调工具；用全能编程 Agent 框架跑日常任务；全程截图让 AI 读数。

| 8 | 第三方工具对拼多多支持不完整 | 中 | 半自动程度下降 | 试用 1–2 款后再定 |
| 9 | 飞书卡片回调在本地部署下不可用 | 低 | 交互受限 | 内网穿透兜底 |
| 10 | 平台规则变化、页面改版 | 中 | 维护成本 | AI 自愈修路 + 失败降级人工 |
| 11 | 拼多多代发考核：发货超时、虚假发货、描述不符被罚款扣分 | 中 | 罚款、限流 | 供应商 48 小时发货率、品质体验分等硬性过滤；在售款每天复查供应商指标；文案和图片不超出实物 |
| 12 | 退货 / 退款吃掉利润 | 高 | 无货源款亏损 | 利润公式计入类目退货损失；上线后用本店真实退货率替换估算值 |
| 13 | 页面用字体混淆或图表图片展示数字 | 未知 | 读文本拿不到数 | POC 阶段 A 确认；如存在则该数据项改用截图识别 |

## 12. 技术方案与代码评审（2026-10-26）

### 12.1 方案评价

| 设计 | 评价 |
|------|------|
| 适配器 + 模拟实现 + 能力开关 | ✅ 不用申请任何账号即可跑通闭环，资质办下一项接一项，适合资质不确定的项目 |
| 三通道自动降级 | ✅ 人工兜底是正式通道，不是事后补丁 |
| 工具三级权限（只读 / 内部 / 写店铺） | ✅ 写店铺前再校验任务状态与店主确认；模型不持有凭证 |
| 状态机 + 人工闸门 + 乐观锁 + 审计 | ✅ 关键决策留给人，可追溯 |
| 自写受控工具循环（不用通用 Agent 框架） | ✅ 有最大轮数和单次 token 上限，成本可控 |
| 数字一致性校验 | ✅ 防模型编数字；⚠️ 序号、数量等普通数字可能被误判，需各智能体配置只校验指定字段 |

### 12.2 关注点

1. **先写代码、后做验证，顺序有些倒置**：POC 阶段 A 尚未执行，后端已约 4500 行，含 AI 认路、脚本转正、熔断等较重机制。若 POC 发现后台读不稳，这部分需大改。**建议 POC 阶段 A、B 完成前不加新功能，只做修补。**
2. **依赖本地单机**：浏览器登录态、SQLite、web 与 worker 两个进程都在一台电脑上，需写清备份与恢复方案。
3. **飞书卡片回调走长连接**仍待验证，不通则需内网穿透。
