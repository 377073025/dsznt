## 1. 设计目标与约束

| 目标 / 约束 | 落到设计上 |
|-------------|------------|
| 人工尽量少 | 每个外部能力都有「能力开关」和降级路径；申请没下来，系统照样能跑，只是走更低一级的通道 |
| 申请进度不确定 | 外部依赖全部通过**适配器接口**接入；同一接口可以有 API 实现、网页实现、人工导入实现，按能力开关自动选 |
| 本地部署 | 单台 Windows 主机，不需要公网 IP；数据和凭证都在本机 |
| 先跑起来再扩展 | MVP 用 SQLite + 两个进程；接口按 PostgreSQL 兼容写，后续可迁移 |
| 安全 | 写操作必须经过状态机闸门；网页读取层只读；凭证不落明文 |
| 成本 | LLM 调用统一经过一个网关，计量、限额、缓存、Batch 都在网关里做 |

## 2. 部署架构

### 2.1 进程与组件

```
┌──────────────────────────── 本地主机（Windows，常开） ────────────────────────────┐
│                                                                                │
│  进程 A：web（FastAPI + Uvicorn）              进程 B：worker                       │
│  ├─ REST API（给 Web 控制台）                 ├─ 调度器（APScheduler）               │
│  ├─ 静态文件（React 构建产物）                 ├─ 作业执行器（从 job 表领任务）         │
│  └─ 只读查询 + 发起人工动作                    ├─ 飞书长连接客户端（事件 + 卡片回调）    │
│                                               ├─ 浏览器池（Playwright，独立 Chrome） │
│                                               └─ LLM 网关（计量 / 限额 / Batch 轮询） │
│                       │                                    │                   │
│                       └──────────── SQLite（WAL 模式）──────┘                   │
│                                                                                │
│  data/                                                                         │
│  ├─ app.db              数据库                                                  │
│  ├─ browser_profiles/   各平台独立浏览器配置（登录会话）                            │
│  ├─ assets/             素材库（原图、AI 产物、历史版本）                          │
│  ├─ imports/            人工导入的原始文件（保留 90 天）                           │
│  ├─ packages/           上架物料包                                              │
│  ├─ page_samples/       网页读取的页面文本样本（用于脚本回归测试，脱敏）              │
│  └─ logs/                                                                      │
└────────────────────────────────────────────────────────────────────────────────┘
         │ 出站 HTTPS（无入站）
         ├─ 飞书开放平台（长连接）        ├─ LLM 服务
         ├─ 拼多多开放平台 / 后台网页      ├─ 1688 开放平台 / 网页
         ├─ 市场数据工具 / 铺货代发工具网页  └─ 生图服务
```

**为什么拆两个进程**：web 进程只做查询和发起动作，重启不影响采集与飞书连接；所有耗时任务都在 worker。两者只通过数据库通信（job 表 + 事件表），不需要消息队列。

### 2.2 运行要求

| 项 | 要求 |
|----|------|
| 主机 | 常开、关闭睡眠；8 GB 内存以上；SSD 剩余 50 GB 以上 |
| 软件 | Python 3.12、Node 20（仅构建前端时）、Chrome（Playwright 自带或系统 Chrome） |
| 网络 | 能访问上述外部服务；不需要公网 IP 与端口映射 |
| 守护 | 两个进程用 Windows 计划任务开机自启 + 看门狗脚本（崩溃 30 秒内重启） |
| 备份 | 每日 03:00 备份 app.db 与 assets/ 增量到另一块盘或网盘目录，保留 30 天 |

## 3. 模块划分与依赖规则

在 02 号文档 2.2 目录规划基础上，规定依赖方向（只能从上往下调用）：

```
interfaces（飞书处理器、REST 路由）
    ↓
workflow（状态机、编排、调度、降级）
    ↓
agents（CEO / 选品 / 运营 / 执行）  ←→  rules（纯函数，可被任意上层调用）
    ↓
tools（readonly / write，智能体唯一能碰外部的入口）
    ↓
data（通道路由、标准化、校验、仓储）
    ↓
adapters（pdd、alibaba1688、market_tool、dropship_tool、image_gen、feishu、llm）
```

| 规则 | 说明 |
|------|------|
| 智能体不直接调适配器 | 只能调注册给它的工具；工具再调 data 层或适配器 |
| rules 无副作用 | 输入数据 → 输出结果，不读数据库、不调 LLM，方便单测与回测 |
| 写操作只有一条路 | `tools/write/*` → 校验任务状态与写入确认 → 适配器；其他模块里没有写店铺的代码 |
| 适配器不含业务逻辑 | 只负责「拿到 / 送出」和格式转换 |

## 4. 能力开关（Capability）

申请下来一项，打开一项；没下来的自动走降级。这是本系统应对「申请进度不确定」的核心机制。

### 4.1 能力清单

| 能力键 | 依赖的申请 | 打开后 | 未打开时 |
|--------|------------|--------|----------|
| `llm` | R06 | 所有智能体可用 | **必需**，系统只能采集数据，不出分析 |
| `feishu_bot` | R04 R05 | 飞书推送、拍板、对话、收文件 | 只能用 Web 控制台拍板；人工导入改为 Web 上传 |
| `pdd_web` | R01 R13 | 拼多多后台数据走网页读取 | 拼多多数据全部走人工导入 |
| `pdd_api` | R07 | 商品、订单走 API；有写权限时可 API 上架 | 走 `pdd_web` |
| `alibaba_web` | R02 R13 | 1688 搜索、详情、以图搜走网页读取 | 选品只能用人工粘贴的货源链接 |
| `alibaba_api` | R08 | 1688 搜索、详情、以图搜走 API（稳定、无风控） | 走 `alibaba_web` |
| `market_tool` | R10 | 热词、榜单、竞品数据来自市场工具 | 用拼多多前台网页读取（每日限 20 页） |
| `dropship_tool` | R03 R09 | 铺货推送、代发自动下单标记 | 物料包 + 人工上传；代发标记按「未知」处理，打分该项记 0 |
| `image_gen` | R11 | 修图、换背景、场景图 | 只从素材库选图 + 程序裁剪/加字 |
| `tunnel` | R12 | 飞书卡片回调走 HTTP 回调地址 | 仅在长连接收不到卡片回调时才需要 |

### 4.2 状态与健康检查

```
not_configured ──(录入凭证)→ configured ──(健康检查通过)→ healthy
                                  ↑                          │
                                  └────(检查失败 3 次)── degraded ──(熔断/过期)→ blocked
```

- 每个能力实现一个 `health_check()`：API 类调一个只读接口；网页类打开首页判断是否仍登录；LLM 发一个极短请求
- 每 30 分钟检查一次；状态变化写 `capability_event`，进入 `degraded`/`blocked` 时飞书通知（若飞书本身不可用则只在 Web 首页红灯）
- 通道路由（第 6 节）只选 `healthy` 的能力
- Web「接入状态」页按 08 号清单的编号展示每项申请的进度和对应能力状态，人工在这里录入凭证

### 4.3 凭证存储

| 类别 | 存法 |
|------|------|
| API Key、App Secret、Access Token | Windows 凭据管理器（Python `keyring`），数据库只存引用名 |
| 浏览器登录会话 | `data/browser_profiles/<platform>/`，目录权限仅当前用户；不导出 Cookie |
| Token 刷新 | 拼多多 / 1688 的 access_token 到期前 7 天自动刷新；失败则飞书提醒店主重新授权 |
| 日志 | 统一脱敏过滤器：token、手机号、地址、身份证号、Cookie 一律打码 |

## 5. 适配器接口

所有外部依赖按下面的接口实现，一个接口可以有多个实现（API / 网页 / 人工导入 / 模拟）。以下为 Python 签名草案，字段以实际实现为准。

```python
# adapters/pdd/base.py
class PddShopAdapter(Protocol):
    def list_goods(self, shop_id: str) -> list[GoodsInfo]: ...
    def goods_daily_traffic(self, shop_id: str, day: date) -> list[GoodsTraffic]: ...   # 访客、加购、下单
    def order_stats(self, shop_id: str, day: date) -> OrderStats: ...
    def promotion_daily(self, shop_id: str, day: date) -> list[PromotionStat]: ...
    def keyword_insight(self, keywords: list[str]) -> list[KeywordStat]: ...
    # 写操作单独一个接口，只有 tools/write 能拿到实例
class PddShopWriter(Protocol):
    def create_goods_draft(self, pkg: ListingPackage) -> WriteResult: ...
    def update_goods(self, goods_id: str, patch: GoodsPatch, before: GoodsInfo) -> WriteResult: ...

# adapters/alibaba1688/base.py
class SourcingAdapter(Protocol):
    def search_by_keyword(self, kw: str, filters: OfferFilter, limit: int) -> list[OfferBrief]: ...
    def search_by_image(self, image: Path, limit: int) -> list[OfferBrief]: ...
    def offer_detail(self, offer_id: str) -> OfferDetail: ...          # 价格阶梯、SKU、库存、代发、发货率、回头率
    def supplier_profile(self, member_id: str) -> SupplierProfile: ...

# adapters/market_tool/base.py
class MarketDataAdapter(Protocol):
    def hot_keywords(self, category: str, week: str) -> list[KeywordStat]: ...
    def category_ranking(self, category: str, week: str) -> list[RankItem]: ...
    def competitor_goods(self, goods_url: str) -> CompetitorGoods: ...

# adapters/dropship_tool/base.py
class DropshipAdapter(Protocol):
    def check_auto_order(self, offer_id: str) -> AutoOrderStatus: ...  # 是否支持自动下单、绑定状态
    def push_listing(self, pkg: ListingPackage) -> WriteResult: ...    # 写操作，同样只在 tools/write 可用
    def order_sync_status(self, day: date) -> list[DropshipOrder]: ...

# adapters/image_gen/base.py
class ImageGenAdapter(Protocol):
    def remove_background(self, img: Path) -> Path: ...
    def replace_background(self, img: Path, prompt: str) -> Path: ...
    def compose_scene(self, product_img: Path, prompt: str, ref: Path | None) -> Path: ...

# adapters/feishu/base.py
class FeishuAdapter(Protocol):
    def send_card(self, chat_id: str, card: dict) -> str: ...          # 返回 message_id
    def update_card(self, token: str, card: dict) -> None: ...         # 延时更新
    def send_text(self, chat_id: str, text: str) -> str: ...
    def download_file(self, message_id: str, file_key: str) -> Path: ...

# adapters/llm/base.py —— 模型服务也做成适配器，便于切换服务商或按地区合规要求调整
class LLMClient(Protocol):
    def run(self, req: LLMRequest) -> LLMResult: ...                   # 同步（流式内部处理）
    def submit_batch(self, reqs: list[LLMRequest]) -> str: ...
    def batch_results(self, batch_id: str) -> list[LLMResult] | None: ...
```

**每个接口都有 `Fake` 实现**（读本地 JSON），用于开发与测试，不依赖任何申请。

## 6. 数据层

### 6.1 数据项定义

每个数据项是一份声明式配置（`data/items/*.yaml`），通道路由器据此调度：

```yaml
item: goods_daily_traffic
schema: GoodsTraffic                # 标准化后的结构
required_fields: [goods_id, day, visitors, add_to_cart, orders]
schedule: "30 6 * * *"
deadline_minutes: 90                # 超时仍无数据 → 标记缺失，下游不分析
channels:                           # 按顺序尝试，跳过能力未 healthy 的
  - {type: api,    capability: pdd_api,  impl: pdd.api.goods_daily_traffic}
  - {type: web,    capability: pdd_web,  script: pdd_backend.goods_traffic_daily}
  - {type: manual, template: 拼多多后台-商品数据-导出.xlsx, guide: guides/pdd_goods_export.md}
```

### 6.2 通道路由与采集作业

```
Scheduler 触发 → 建 fetch_job(scheduled)
Executor 领取 → 依次尝试 channels：
   api    → 调接口 → normalizer → validator → 入库 → success
   web    → 浏览器池拿会话 → 跑脚本 → normalizer → validator → 入库
            ├ 脚本失败 → AI 认路（6.4）
            ├ 验证码 / 登录失效 → waiting_human（飞书「需要人工」卡片）
            └ 风控提示 → circuit_open（6.5）
   manual → 飞书发「请导出 xx」卡片 + 图文指引 → manual_requested
            用户把文件发给机器人或在 Web 上传 → 解析 → 入库 → success
成功后发事件 data_ready(item, day) → 下游作业（指标计算、分析）按依赖自动触发
```

- 同一 `(item, day)` 同时只允许一个作业；重复触发直接复用
- 入库按 `(item, key, day)` 幂等覆盖，人工补导的数据可覆盖 API/网页数据并留痕
- 下游依赖声明在作业定义里：如 `ops_analysis` 依赖 `goods_daily_traffic`、`goods_snapshot`、`order_stats` 三项均 ready

### 6.3 网页读取脚本格式

脚本是数据（YAML），不是代码，这样 AI 修路时只生成步骤，不生成可执行代码，执行器可以逐步校验。

```yaml
task: pdd_backend.goods_traffic_daily
version: 4
platform: pdd_backend
updated_by: ai            # ai / dev
params: {day: "{{yesterday}}"}
steps:
  - goto: "{{urls.goods_data}}"                # 入口地址放在平台配置里，不写死
  - wait_for: {role: table, name_contains: "商品明细"}
  - click: {role: button, name: "日"}          # 只允许白名单动作
  - set_date: {target: {role: textbox, name_contains: "日期"}, value: "{{day}}"}
  - read_table: {target: {role: table, name_contains: "商品明细"}, paginate: {role: button, name: "下一页"}, max_pages: 20}
  - map_columns: {商品ID: goods_id, 访客数: visitors, 加购件数: add_to_cart, 支付订单数: orders}
```

**动作白名单**：`goto`（限平台域名）、`wait_for`、`click`、`set_date`、`fill_search`、`select_option`、`read_text`、`read_table`、`download_export`、`screenshot_region`、`map_columns`。

**黑名单校验**：`click` 目标的名称或附近文本命中「提交 / 保存 / 发布 / 删除 / 确认修改 / 上架 / 下架 / 付款 / 下单」等词时拒绝执行，作业失败并记录。

### 6.4 AI 认路

```
脚本某步失败（元素找不到 / 结果为空 / 列名对不上）
 → 截取当前页面无障碍树（裁剪到 ≤ 8k token）+ 任务目标 + 原脚本 + 失败步骤
 → Sonnet 5.5 返回下一步动作（必须是白名单动作，JSON 格式）
 → 执行器校验并执行 → 回传新页面状态 → 循环，最多 15 步
 → 拿到目标数据且通过 validator → 把实际走过的步骤整理为新版本脚本（version+1，updated_by=ai）
 → 新脚本先进入 candidate 状态，连续 2 次成功后转正；期间旧脚本保留
 → 失败 → 降到 manual 通道
```

- 每次认路记录 token 与步骤，计入 `llm_usage`（agent=`web_repair`）
- 同一脚本 24 小时内认路超过 3 次 → 停用该脚本，提示开发者检查

### 6.5 限速与熔断

| 机制 | 实现 |
|------|------|
| 限速 | 每平台一个令牌桶，参数来自规则配置（02 号 3.3 节默认值）；1688 每日页面上限达到后当天停止 |
| 时间窗口 | 网页读取只在 08:00–23:00 的随机间隔内执行（1688），拼多多后台在 06:00–08:00 集中执行 |
| 风控识别 | 页面文本或 URL 命中「验证 / 滑块 / 安全检测 / 访问受限 / 账号异常」→ 立即停止该平台所有作业 |
| 熔断 | 验证码类：`waiting_human`，人工处理后恢复；限制类：`circuit_open` ≥ 24 小时，必须店主确认恢复 |
| 记录 | 每次触发写 `risk_event`（含触发前 1 小时请求速率），月度复盘调整限速参数 |

### 6.6 人工导入

| 环节 | 设计 |
|------|------|
| 入口 | 飞书私聊/群聊直接发文件给机器人；或 Web「数据中心 → 上传」 |
| 识别 | 按表头特征匹配解析器（不依赖文件名）；识别不了时回复「这份文件我不认识，是哪个页面导出的？」并给出选项 |
| 解析器 | 每种导出模板一个解析器 + 一份样例文件，模板变化时用样例回归测试 |
| 校验 | 必填字段、日期范围、数字合理性；不通过时在飞书列出具体行 |
| 回执 | 「已导入 2026-10-23 商品数据 48 行，下游分析已重新开始」 |

### 6.7 快照对比生成改动事件

每日商品快照对比前一天：标题变化、主图哈希变化、价格变化、SKU 增删 → 生成 `change_event(source=snapshot)`。若同一改动已由系统任务登记（`source=task`），按商品 + 类型 + 48 小时窗口去重。

## 7. 智能体运行时

### 7.1 统一执行框架

所有智能体继承同一个运行器，区别只在提示词、工具集、模型、限额：

```python
@dataclass
class AgentSpec:
    name: str                     # selection.demand_scout / ops.diagnose / ceo.daily ...
    model: str                    # claude-sonnet-5-5 等，来自配置
    system_prompt: str            # prompts/<name>.md，固定在前以便缓存
    tools: list[ToolDef]          # 只读或写工具，按角色注册
    output_schema: type[BaseModel]   # 结构化输出，pydantic 校验
    max_turns: int = 6
    max_tokens_per_run: int = 30_000
    use_batch: bool = False       # 每日运营分析、每周同款/合规审查为 True
```

运行流程：

```
组装输入（程序已汇总的数据）
 → LLM 网关：检查日预算 → 调模型（工具循环 ≤ max_turns）
 → 输出按 output_schema 校验 → 失败重试 1 次
 → 数字一致性校验（7.3）→ 失败重试 1 次，仍失败丢弃该条
 → 写结果表 + llm_usage → 发领域事件
```

### 7.2 工具注册

| 智能体 | 可用工具 |
|--------|----------|
| 选品 · 需求侦察 | `get_top_goods`、`get_keyword_stats`、`get_category_ranking`、`get_competitor`（只读） |
| 选品 · 同款审查 / 合规审查 | `get_offer_detail`、`get_image`（只读）；输入里直接带图片 |
| 选品 · 推荐撰写 | 无工具，只读输入 |
| 运营 · 诊断 / 建议 / 复盘 | `get_metrics`、`get_change_events`、`get_goods_snapshot`、`compare_periods`（只读） |
| CEO · 汇总 | 无工具，输入为各智能体输出 |
| CEO · 派活 | `create_task`（写任务表，不写店铺） |
| CEO · 验收 | `get_task_output`、`get_image`、`check_live_goods`（只读，触发一次网页读取核对） |
| 执行 · 文案 | `check_forbidden_words`（只读） |
| 执行 · 图片 | `asset_search`、`image_edit`（写素材库） |
| 执行 · 上架 | `build_package`（写产物区）、`push_to_dropship_tool` / `pdd_create_draft`（**写店铺**，需 `write_confirm`） |

写店铺的工具内部再查一次：`task.status == writing` 且存在 owner 的 `write_confirm` 记录，否则拒绝并告警。

### 7.3 数字一致性校验

- 输入数据在组装时生成「事实表」：每个数值带来源键（如 `goods.c_12.visitors_7d = 1320`）
- 输出中的每个数字（含百分比、金额）用正则抽出，必须能匹配事实表中的值，或能由事实表中两个值经允许的运算（差、比、百分比变化）得出，容差 ±0.5%
- 程序侧计算好的派生值（转化率、毛利）直接放进事实表，减少模型自己算
- 不匹配的数字列出来让模型重写一次；仍不匹配则丢弃该条建议，写 `audit_log`

### 7.4 LLM 网关

| 功能 | 做法 |
|------|------|
| 计量 | 每次调用记录 agent、模型、输入/输出/缓存读取 token、费用 |
| 预算 | 日预算、月预算（规则配置）；超日预算 80% 告警，100% 时非关键任务（复盘解读、月度调权）推迟到次日，关键任务（日报、拍板相关）照常 |
| 缓存 | 系统提示词 + 工具定义 + 规则说明放在请求最前并标记缓存 |
| Batch | 标记 `use_batch` 的任务提交 Batch，worker 每 10 分钟轮询结果；早报所需的分析在 06:45 提交，07:30 前未返回则改走实时调用 |
| 重试 | 限流 / 过载按指数退避重试 3 次；仍失败标记任务失败，早报中注明「该部分今日缺失」 |
| 模型配置 | 模型名只出现在配置文件，代码里用角色名（`model.ceo`、`model.main`、`model.light`） |

### 7.5 提示词管理

- `prompts/<agent>.md`，带版本号；每次运行记录使用的提示词版本
- 选品同款审查、合规审查各有一份评测集（POC 阶段 A 的 50 对标注 + 后续误判样本），提示词修改后先跑评测，准确率不降才能上线

## 8. 工作流引擎

### 8.1 状态机实现

各实体状态机（02 号第 5 节）统一用「转换表」实现：

```python
TRANSITIONS = {
  ("suggestion", "reported", "approve"):  Transition(to="approved",  allowed_roles={"owner"}),
  ("suggestion", "reported", "reject"):   Transition(to="rejected",  allowed_roles={"owner"}),
  ("suggestion", "reported", "revise"):   Transition(to="revising",  allowed_roles={"owner"}),
  ("task", "awaiting_write_confirm", "confirm"): Transition(to="writing", allowed_roles={"owner"}),
  ("fetch_job", "circuit_open", "resume"): Transition(to="scheduled", allowed_roles={"owner"}),
  # ...
}

def transition(entity, event, actor) -> None:
    # 1. 查表，不存在则拒绝
    # 2. 校验 actor 角色；actor 为 agent 时不能触发 allowed_roles 中只含人类角色的转换
    # 3. 乐观锁：UPDATE ... WHERE id=? AND status=? AND version=?
    # 4. 写 audit_log，写 domain_event（outbox）
```

- **人工闸门硬编码**：`approve`、`confirm`、`resume`、`accept_test_verdict` 只允许人类角色；智能体的 actor 类型是 `agent`，在转换函数里直接拒绝
- **领域事件**：写 `domain_event` 表，worker 轮询（1 秒）分发给订阅者，例如 `suggestion.approved → ceo.dispatch`

### 8.2 编排

| 流程 | 编排方式 |
|------|----------|
| 每日运营闭环 | 依赖图：数据项 ready → 指标计算 → 运营分析 → CEO 汇总 → 发早报；任一节点缺失，下游跳过并在早报标注 |
| 每周选品 | 依赖图：需求侦察 → 货源匹配（分批采集，前一周已在进行）→ 过滤 → 审查 → 打分 → 推荐 → CEO 周报 |
| 拍板后执行 | 事件驱动：approved → 派活 → 各执行任务并行 → 全部 produced → 写入确认（如需）→ 提交 → 验收 |
| 到期复盘 | 改动事件登记时生成到期作业（默认 7 天）；测款上架时生成 14 天到期作业 |

### 8.3 超时与提醒

| 等待状态 | 提醒 | 超时处理 |
|----------|------|----------|
| 建议 `reported` 未拍板 | 当天 20:00 提醒一次 | 48 小时后自动过期 `expired`，不执行 |
| 写入确认未处理 | 2 小时后提醒 | 24 小时后取消该写入，任务回到 `produced` |
| 人工导入 `manual_requested` | 30 分钟后提醒（须短于截止时间） | 到 `deadline` 标记缺失，其余数据结束后带着缺失出早报 |
| 验证码 `waiting_human` | 30 分钟后提醒 | 不超时，持续暂停该平台 |

## 17. 智能体独立运行与单独任务

需求见 01 号 F11，产品设计见 02 号 4.6。目标：每个智能体能力可单独调用；后台可见每个智能体在做什么；人工可提交单独任务；**不影响主流程**。

### 17.1 现状与改造点

| 现状（代码） | 问题 | 改造 |
|--------------|------|------|
| `workflow/pipelines.py` 里各流程直接组装输入、调用 `AgentRunner.run` 并处理结果 | 智能体能力和主流程绑在一起，无法单独调用 | 抽出「能力注册表」（17.2），主流程改为调用能力 |
| `worker.py` 只有一个作业循环，按 `job.id` 顺序领取 | 单独任务会和主流程抢同一个循环，早报可能被拖慢 | `job` 加 `lane` 字段，分两个执行循环（17.4） |
| 只有 `llm_usage` 记录调用费用 | 看不到智能体「此刻在干什么」 | 新增 `agent_run` / `agent_run_step`，由运行器写入（17.3） |

### 17.2 能力注册表

每个智能体能力注册为一个 `Capability`，主流程和单独任务共用：

```python
@dataclass(frozen=True)
class Capability:
    key: str                          # "selection.evaluate_offer"
    agent: str                        # "selection"，工作台按它分组
    title: str                        # "单品评估"
    params: type[BaseModel]           # 人工提交时的参数（Web 表单由它的 JSON Schema 生成）
    run: Callable[[CapContext, BaseModel], BaseModel]   # 组装输入 → AgentRunner → 结构化输出
    uses_web: set[str] = frozenset()  # 需要的网页读取平台，如 {"alibaba"}
    adhoc: bool = True                # 是否允许单独调用
    promote_to: Literal["suggestion", "candidate", "task", None] = None   # 可转成什么

CAPABILITIES: dict[str, Capability] = {}
```

- `run` 只负责「输入 → 输出」，**不写主流程的业务表**（不建 suggestion、不发早报、不派活）。
- 主流程编排拿到输出后，自己决定写入哪些业务表；单独任务则把输出存进 `adhoc_task.result_json`。
- 首批注册的能力即 02 号 4.6「可单独调用的能力」表；新增智能体只要注册能力，就自动出现在工作台。

### 17.3 运行记录与实时状态

`AgentRunner.run` 增加一个 `RunTracker` 参数，在以下时点写库（每次独立短事务，不和业务事务混在一起，避免业务回滚时状态也丢失）：

| 时点 | 写入 |
|------|------|
| 开始 | `agent_run`：status=running、来源、started_at |
| 每次调用模型前 | current_step=「等待模型（第 n 轮）」 |
| 每次调用工具 | current_step=「调用工具 xxx」；追加 `agent_run_step`（参数与结果摘要） |
| 格式 / 数字校验重试 | current_step=「数字校验重试」；追加步骤 |
| 每轮结束 | turns、tokens、cost_fen 累加；**检查 `cancel_requested`，为真则抛出 `RunCancelled`** |
| 结束 | status=succeeded / failed / cancelled、finished_at、error |

**智能体状态的计算**（Web 查询时实时算，不单独存）：

| 状态 | 判断 |
|------|------|
| 运行中 | 该智能体有 `agent_run.status = running` |
| 等待人工 | 该智能体相关任务处于 `awaiting_write_confirm`，或其需要的平台处于 `waiting_human` |
| 已暂停 | 其能力依赖的 capability 未就绪 / 熔断，或预算已用完 |
| 排队中 | 有该智能体的 `job.status = queued` |
| 空闲 | 以上都不是 |

**清理**：`agent_run_step` 保留 30 天，`agent_run` 保留 180 天；worker 重启时把 `running` 超过 30 分钟的运行标记为 failed（与作业恢复同一时机）。

### 17.4 双通道执行（不影响主流程的关键）

```
worker 进程
├─ 主线程：飞书长连接（SDK 要求）
├─ 线程 1：主通道循环   只领 lane=main 的作业（定时流程、事件、拍板后执行）
├─ 线程 2：单独通道循环 只领 lane=adhoc 的作业，同一时间最多 1 个
└─ 调度器线程
```

- `_claim(s, worker_id, lane)` 按通道领取；两个循环互不等待，主流程作业永远不会排在单独任务后面。
- 每个线程用自己的数据库会话；SQLite 已开 WAL，设置 `busy_timeout=5000`，写事务保持短小。
- **浏览器互斥**：每个平台一把锁（`browser_lock[platform]`，进程内 `threading.Lock`）。单独任务拿锁时：
  - 在主流程采集时段（`adhoc.web_blackout`，默认 06:00–08:30）内 → 不等待，作业 `run_after` 顺延到时段结束；
  - 主流程正在用该平台 → 等待最多 10 分钟，超时顺延；
  - 主流程拿锁时若单独任务正在用 → 等它读完当前页（单页粒度释放），不打断主流程。
- **页数额度**：每个平台的每日页数上限中，单独任务最多占 `adhoc.web_page_ratio`（默认 20%），由限速器按通道分别计数；用完则该任务 `deferred` 到次日。
- **预算**：LLM 网关按 `lane` 分别计数。单独任务有独立的 `adhoc.daily_cny`（默认 ¥2）；超额时抛出 `BudgetExceeded`，作业顺延到次日，不计失败次数（沿用现有处理）。主流程预算与关键任务规则不变，且单独任务的花费不计入主流程的日预算判断。

### 17.5 单独任务

**提交与执行**

```
Web 表单提交（或飞书指令，P1）
 → web 进程：校验角色（owner / operator）、按 Capability.params 校验参数
 → 写 adhoc_task(status=queued) + job(type="adhoc.run", lane="adhoc", payload={adhoc_task_id})
 → worker 单独通道领取 → 检查浏览器时段 / 页数额度 / 预算 → 调用 Capability.run（source=adhoc）
 → 结果写 adhoc_task.result_json，status=done / failed
 → （P1）飞书通知提交人
```

**结果隔离的三条硬规则**

1. 单独任务的 `ToolContext` 带 `lane="adhoc"`，工具注册表对 `shop` 级工具**直接拒绝**并写审计，所以单独任务无法写店铺。
2. 单独任务不写领域事件 `domain_event` 中主流程订阅的类型；它只产生 `adhoc.*` 事件（用于通知），主流程订阅者不处理。
3. `Capability.run` 本身不写主流程业务表（17.2），结果只在 `adhoc_task` 里。

**转为建议 / 转为任务**：人工点击后，web 进程按 `promote_to` 创建 `suggestion`（status=reported）或 `candidate`（status=recommended）或 `task`（status=pending，需派活与写入确认），记录 `source=adhoc`、`adhoc_task_id`，`adhoc_task.status=promoted`。之后完全走主流程的状态机和人工闸门，没有任何捷径。

**取消**：`queued` 直接改为 `cancelled` 并删除对应作业；`running` 时置 `agent_run.cancel_requested=true`，运行器在下一轮开始前停止（已发出的模型调用会正常结束并计费）。

### 17.8 异常与降级

| 情况 | 处理 |
|------|------|
| 单独任务预算 / 页数额度用完 | `deferred` 到次日，工作台显示原因；主流程不受影响 |
| 单独任务需要的平台熔断或未登录 | 不运行，状态「已暂停」并提示原因；不触发额外的人工通知（避免和主流程重复） |
| 单独任务失败 | 不自动重试（与主流程不同），结果页显示错误，人工可「重新提交」 |
| worker 重启 | 运行中的单独任务标记 failed，可重新提交 |
